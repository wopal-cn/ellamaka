# 项目规范加载设计

> **Status**: Active
> **Updated**: 2026-11-25
> **Parent**: `./DESIGN.md` — 展开主设计中的会话指令加载契约
> **Parent Architecture**: `../../../docs/products/wopal-space/DESIGN.md`
> **Parent Product**: `../../../docs/products/wopal-space/PRD.md`
> **Scope**: Agent 读取、创建和修改项目文件时，怎样获得适用的 AGENTS.md 规范，以及如何在长会话中持续遵守这些规范。

Agent 在项目内操作文件时，需要先知道该遵守哪些规则。一个项目可以在根目录和不同子目录分别放置 `AGENTS.md`。越靠近目标文件的规则越具体。

系统按两种时机提供规则：

- **每次请求模型时**，提供用户全局规则和当前会话目录的项目规则。
- **进入更深目录操作文件时**，提供该目录及途经子目录的规则；规则要在模型作出修改决定前可见。

是否已经提供过规则，以**模型本次还能看到的消息**为准。数据库里保存过旧消息，不表示压缩后的模型仍能看到它。

## Instruction Sources

| 来源            | 位置                                     | 说明                                                |
| --------------- | ---------------------------------------- | --------------------------------------------------- |
| 用户全局        | `$WOPAL_HOME/AGENTS.md`                  | 进程级用户指令                                      |
| 用户全局 Claude | `~/.claude/CLAUDE.md`                    | 只在未启用 WopalSpace 模式的运行里参与              |
| 项目链          | 会话目录到 worktree 根之间的 `AGENTS.md` | 每个祖先目录命中的文件都进入基线                    |
| 项目链候选      | `CLAUDE.md`、`CONTEXT.md`                | 候选顺序为 `AGENTS.md` → `CLAUDE.md` → `CONTEXT.md` |
| 配置追加        | `ellamaka.instructions`                  | 支持相对 glob、绝对路径与 `http(s)://` URL          |

候选文件族的作用规则：基线按候选顺序逐个探测，第一个在项目链上出现命中的文件族决定整条项目链使用哪个名字，其余候选不再探测。WopalSpace 模式的候选集合是 `AGENTS.md` 与 `CONTEXT.md`，`CLAUDE.md` 由空间自己的规范入口取代。

## Baseline Loading

- **解析时机**：每次模型请求构建 system prompt 时解析。文件变化在下一请求生效，不需要新会话。
- **作用域**：用户全局文件、从会话目录向上到 worktree 根的项目链、`ellamaka.instructions` 配置项。
- **呈现**：每个文件渲染为一个 `Instructions from: <path>` 段落，进入 system prompt 的指令区，读者与模型都能看到来源。
- **界面来源记录**：系统另外把本次基线加载的文件路径写成 `ignored: true` 的合成文本（仅用于界面展示，不进入模型输入）。该记录按“当前压缩边界之后最近一次已记录的来源列表是否变化”去重：基线未变化时不重复写入；同一用户消息的多步工具循环中基线变化时原地更新该条记录；压缩完成后的下一次正常用户请求再重新写入一次。
- **边界**：worktree 之上不读取；相对配置路径从会话目录向上解析；远程配置项按 URL 读取。
- **失败处理**：单个规则文件读取失败时，其余规则照常提供。修改前检查遇到无法读取的适用规则时，暂停文件修改并说明原因。

## Directory-Level Attachment

- **读取时机**：Agent 用 `read` 或 `str_replace_editor` 的 `view` 命令成功读取文件，或者用户在聊天中附加可以定位到项目目录的本地文件时，把适用规则附在读取结果后面。无论读的是文本、图片还是 PDF，都保留原本的内容或附件；目录 `view` 仅列举目录，不挂载文件级规范。
- **文件位置**：从目标文件所在目录向上查找，一直到会话目录。会话目录已经在每次请求的基础规则中，不再重复。只有目录列举、读取失败、没有适用规则时不增加内容。
- **路径处理**：相对路径以当前会话目录为准；对已存在的目标解析符号链接，按实际目标所在目录查找规则。创建新文件时，从最近的已存在父目录解析真实路径，再拼接尚不存在的路径部分。只有实际目标属于会话项目的有效目录链时才挂载目录规范；指向项目外的符号链接不扩展加载边界或原工具的访问权限。目录边界使用真实的父子关系，不能把名字前缀相同的另一个目录当成同一项目。
- **选择规则**：在每级目录按现有候选顺序选择规则文件；直接读取规则文件本身时，保留它的原始内容，不额外附加自身。
- **提供方式**：文件正文或附件照常返回，另外附上标明来源的 `<system-reminder>` 文字，供模型后续决策使用。
- **同批去重**：一次模型请求内并行发出的多个工具调用构成一批。同一份规则正文在一批结果里最多出现一次：最先命中的结果附上正文，同批其余结果不再重复附加。因修改前检查而暂停的操作同样不重复正文，只返回“规则已在同批其他结果中提供”的重试提示。模型在同批内看得到那条结果，去重不减少它实际可用的规则。

读取是安全的发现机会：它可以先完成，然后把规则与文件一起交给模型。修改文件则必须先检查规则。

## Before File Changes

当 Agent 使用 `write`、`edit` 或 `str_replace_editor` 创建、覆盖、编辑项目文件时，系统在**真正修改文件之前**检查目标目录的规则。

- 模型本次请求中已经看到适用规则：按原有权限与文件工具流程执行修改。
- 目录没有额外规则：按原有流程执行修改。
- 有适用规则，但模型本次没有看到：**本次不修改文件**。系统把规则交给模型，并明确告知“文件尚未修改，请按规则重新发起操作”。模型在下一次请求中看到规则后才能重试。
- 规则文件存在却无法读取：停止这次修改，说明无法加载哪一份规则；不能把“加载失败”当成“没有规则”。

这项检查不取代工具本身的权限审批、文件版本检查或读后修改保护。即使某个工具允许直接创建文件，也必须先确认模型已经得到目标目录的规则。

同一批并行工具调用中，某个 `read` 刚产生、但模型尚未看到的规则，不能算作已经提供给模型。修改工具按**发起这批调用时的模型上下文**判断。暂停的修改是一次未执行的文件操作：返回规则与重试提示，但不触发实际工具执行，也不发布表示文件已修改的后续文件操作事件；正常重试成功后仍走原有事件与结果处理流程。

同批去重只影响正文出现在哪条结果里，不改变这条判断：一批之内，规则正文至少会进入其中一条结果，模型在这一轮就能看到它。

## Read Entry Points

模型使用的原生 `read`、DSH 投影 `read` 和 DSH `str_replace_editor view`，都经由 `SessionTools`。这里负责读取成功后的规则加载，也负责 `write`、`edit`、`str_replace_editor` 修改命令执行前的规则检查；`view` 是读取操作，不作为修改拦截。

聊天中附加的本地文件由 `SessionPrompt` 直接读取，不经过 `SessionTools`。这条入口调用相同的规则查找与记录能力，把规则附在给模型的文件文字里。

两种读取入口和修改前检查共享同一套规则，不依赖原生或 DSH 工具怎样实现。工具本身仍只负责读取或修改文件。

## After Context Compaction

上下文压缩会把较早的聊天和工具结果移出模型本次可见的内容。压缩摘要不等于完整的 `AGENTS.md`，即使摘要提到过该文件，也不能当作模型仍然知道规则。

- 用户全局规则和会话目录的项目规则在**每次模型请求**时重新读取，因此压缩后自动恢复。
- 更深目录的规则在**压缩后第一次再次访问该目录**时重新检查：下一次 `read` 会重新提供；下一次 `write` 或 `edit` 会先提供规则、暂停修改，再由模型重试。
- 最近的工具结果如果仍在压缩后保留的模型输入中，且其中确实包含规则全文，就不重复提供。只保留 `metadata.loaded`、来源标题或摘要中的规则文件名，不属于规则全文可见。
- 恢复以前的会话时，同样按恢复后的实际可见内容判断。开启全新会话时，从基础规则重新开始。

系统不会在每次压缩后把所有曾经访问过的目录规则一次性塞回上下文。只恢复这次工作真正用到的规则，避免长期会话越来越臃肿。

## Keeping Track of Loaded Instructions

系统在现有会话消息里记录**这次实际给模型提供了哪份规则**，记录文件的绝对路径即可。模型工具 `read` 用工具结果元数据记录；用户附加本地文件用相应的合成文本元数据记录；修改前暂停的操作也在工具结果正文提供规则，并把已提供的路径记入结果元数据。

`metadata.loaded` 描述的是**这条结果自己附上的规则**。同批去重让规则正文只出现一次，因此一批里只有附了正文的那条结果记录路径，其余结果的 `loaded` 为空数组。空数组表示“这条结果没有新增正文”，不表示“该目录没有规则”；同批内已由其他结果提供的规则仍然算模型已经看到。

检查“是否已加载”时，只使用本次实际转换并送给模型的消息。`metadata.loaded` 仅用于定位候选规则，不能单独证明规则正文可见；只有对应消息中的完整规则正文仍会进入本轮模型输入，才算已加载。历史结果即使带有 `metadata.loaded`，只要正文缺失或已被截断，也必须重新加载；已经压缩掉的旧工具结果、已经清空的工具输出，以及只在历史数据库中存在的记录，同样不能阻止重新加载。同批调用尚未交给模型的规则也不能提前标记为已加载。此判断不比较磁盘上规则文件的新旧内容，也不引入中途变更检测。

记录随着普通会话消息保存和管理，不建立另外一份不断追加的规则清单。记录内容只是规则路径；规范正文只有在需要提供给模型时才加入消息。历史数据库可能随聊天记录增长，但不会因为这一功能产生独立的无限增长缓存。

## Rule File Updates

**本设计不自动检测子目录规范文件在会话中途发生的内容变更。** 同一份规则只要仍在模型本次可见的上下文中，就不因为再次访问目录而重新读取正文。会话压缩清除了这份规则后，或开启新会话时，再次需要它便按磁盘上的现有内容加载。

用户全局规则和会话目录的项目规则仍沿用现有行为：每次模型请求都会重新读取。系统不启动文件监听器、不存储规则内容哈希，也不为子目录规则增加独立的定时检查。

## Business Rules and Failure Boundaries

- **读取失败与修改前阻断**：读取文件成功但规则查找失败时照常返回原文件并记录可诊断错误（不记为已加载）；但使用 `write`、`edit`、`str_replace_editor` 修改前，只要存在未见规则或规则文件不可读，必须暂停本次文件修改并先返回规则正文或明确失败原因，禁止把加载失败当作“无规则”。
- **实际可见性与同批语义**：是否已加载严格以本次仍会进入模型输入的完整规范正文为准（`metadata.loaded` 不可单独充当证明，压缩截断后必须重新加载）；同批并行调用中，`read` 刚产出的规则不免除同批修改工具的事前检查，且同批内去重保证正文至少在首条命中结果中出现一次。
- **范围边界与安全隔离**：规则查找仅限于真实路径属于会话有效目录链的目标，符号链接指向项目外时不扩展加载边界或文件访问权限；Shell 命令与外部 MCP 工具修改文件走各自授权路径。

## Ownership

会话层统一负责规则查找、向模型提供规则、检查当前是否仍有效。它查看本次模型能看到的消息、当前会话目录和目标文件，判断是否需要重新提供。

模型工具 `read`、`write`、`edit` 与 `str_replace_editor` 的结果和修改仍由原有工具负责。会话层只在正确的时机提供规范或暂停尚不符合规范条件的修改。

`ellamaka-tools` 容器不加载 DSH 的指令插件。该插件依赖 agent 循环与 DSH Session，容器两者都没有。

错误按会话日志规则记录，不记录文件正文和规则正文。

## DSH Alignment

DSH 用 `@deepseek-ai/dsh-agent-instructions` 提供目录规则，在成功的 `read`、`write`、`edit` 后发现相关目录，并在后续模型请求中提供或更新规则。

Ellamaka 的 DSH Tools 配置沿用 DSH 默认值，保持 `dsh-fs-observation-policy` 为 `disabled: true`（如需“编辑前先读取”的强制运行期门禁，可在用户 `ellamaka-tools/cordis.patch.yml` 中覆盖该插件的 `disabled` 配置为 `false` 恢复）。文件修改前的 `AGENTS.md` 检查与压缩后恢复由 Ellamaka 会话层独立保证，不依赖这项 DSH 策略，原生工具也同样遵循会话层约束。

Ellamaka 的会话层为两种工具后端提供同样的规范加载行为。修改前检查和上下文压缩后的恢复由 Ellamaka 自己负责，不依赖 DSH 工具容器运行指令插件。
